# Agent Note：面向 RCI 系统的专家通道（HITL）

Status: proposed

[English](2026-11-03-hitl-expert-channel.md) | 中文

## 问题

一个 RCI 系统会无人值守地跑上几周：几十条 Agent loop 各自朝一个目标优化，各自维护工作区、笔记和分数历史。它们卡住的方式，再加多少轮都解不开，因为缺的不是算力，是人类专家掌握而系统测不到的知识：这块硬件实际是怎么表现的、哪个方向已知是死路、团队当前的优先级是什么。

把这种知识接进来需要的是一条闭环，不是一个聊天窗口。问题要带着足够的现场送到专家面前，让他一次就能答；答案要以结构化的立场回来，而不是一段对话记录；系统要真的拿它去做事；专家要知道自己的答案引发了什么，否则他就不答了。四段，缺一段整条链就断：只有聊天没有提取，留下的是没人解析的散文；有提取没有回执，专家是在往黑洞里写建议。

这条闭环已经有一套在本仓库之外运行的部署。它缺的是专家天天在要的那部分的架构：「这个能不能展示一下」「那几条分支的 profiling 长什么样」。现在每一个这样的请求都等于一次开发改代码，所以绝大多数请求根本没被提出，站点停留在通用形态，而每个 RCI 系统的需要都是特定的。

## 方案

把专家通道做成一个一切皆插件的站点——借鉴本仓库的架构，而不是跑在它上面——并加上创造模式：专家的一句话，当分钟就能变成他用得上的插件。

闭环及其契约定义在 [docs/hitl/](../../../../docs/hitl/README.zh.md)：系统侧提问器与收件箱之间的[提问契约](../../../../docs/hitl/question-contract.zh.md)、专家标记已解决之后的[提取与注入](../../../../docs/hitl/extraction-and-injection.zh.md)、[创造模式](../../../../docs/hitl/creator-mode.zh.md)。

三个决定支撑整个设计。

**内核只实现闭环。** 提问摄取、对话、标记已解决、提取、投递、回执是内核。所有系统特定的东西——每一块面板、每一个视图、每一张看板——都是插件。一个新部署靠写提问器、sink 和几个数据提供者来适配，而不是改内核。这一条直接取自本仓库，取它是因为反面已经被观察到：把实例特定的面板编译进核心界面，每一次部署都会变成一个分叉。

**插件运行时加载、按人可见、可撤销。** 构建期的插件清单和创造模式不相容——创造模式的全部价值就在于专家在提出需求的那段对话里就拿到面板。按人可见是防止一百个单用途面板堆在所有人首页的办法；可撤销是让"允许模型写这些东西"这件事变得安全的前提。

**三个 Agent 分开，工具不重叠。** 常驻 Agent 以只读权限看工作区，回答专家。提取 Agent 完全不带工具，只看一段讨论，每次新会话——给它工具它就会拿系统自己的材料去"核实"专家，而这正是提取必须避免的污染。创造 Agent 只能写一个插件目录。这些是权限边界，不是提示词里的叮嘱。

常驻 Agent 的提示词同样是设计决定，不是细节。它的输出会变成专家签字认可的材料，而签字认可的立场会被自动注入。一个爱附和的常驻 Agent 因此会污染系统的输入。提示词要求它中立复述、拿实测证据核对、把矛盾与代价说得和认同一样坦率、只追问真正会改变系统行动的歧义。

## 借鉴了什么，没借鉴什么

借鉴：一切皆插件；清单声明式组合；安装即热加载；以及创造模式的工作流纪律——先查真实 API，从模板起步，经由管理器安装，读取安装是否生效，对着实时状态验证，产物持久化且可撤销。

没借鉴：Cordis 运行时及其依赖注入、`dsh web` 的单所有者令牌鉴权、profile/bundle 的目录结构。这里的插件扩展的是面向人的站点，不是 Agent 运行时；生命周期、权限模型、受众全都不同。

本仓库的 harness 可以承载三个 Agent 中的任何一个，其中最适合创造 Agent——它的插件开发技能里已经写好了上面那套工作流纪律。要换掉的是上面一层：检查工具换成嵌入点清单与数据提供者样例，技能与模板换成 HITL 的。

## Alternatives considered

**用内置的 `ask_user_question` 驱动闭环。** 它看起来正好对上"Agent 自主提问"，但在这里是错的。它的等待状态在进程重启后丢失，而这里的问题要在两侧都重启的情况下存活几周。往系统自己持有的文件里追加一行，还意味着**站点不在时系统照样能提问**，这对长期运行的部署是必需的。收件箱里那条持久的问题记录是权威；这个工具留给创造 Agent 做澄清提问——那种提问本来就是短命的。

**直接用 `dsh web` 服务专家。** 它是单所有者的：一个进程令牌换一个 cookie，没有账号体系。专家通道需要多个具名专家、按人区分的插件可见性，以及每一条被注入的答案上的署名链路。

**用带工具的 Agent 做提取，或在校验失败时回退到原文。** 两者都会让未经校验或已被污染的内容进入系统。提取改为显式失败、专家可见、可点重试。

## Acceptance criteria

- 摄取幂等：重读被重写过的源文件、重复提交同一个问题 id，都不产生重复问题。
- 半行安全：并发写入的源文件不会产出截断的 JSON 对象。
- 提取对缺 `answer` 或 `claim` 为空的响应判不通过，带原因重试一次，最终标记失败而不是改用原文。
- 专家补充新方向后再次标记已解决会再次投递；内容原样未变的重复标记不会。
- 一次主动注入只带走同一对话、同一目标下早先注入未覆盖的内容。
- 构建产物请求了清单 `dataNeeds` 里没声明的数据提供者的插件，安装时被拒绝。
- 不符合声明模式的提供者参数，在进入 argv 或 URL 之前被拒绝。
- 渲染抛异常的插件降级成一张错误卡，不影响其他插件。
- 每一次投递失败、提取失败、插件变更，专家都看得到，且记进事件日志。

## Risks

**模型写出的插件在专家的浏览器里执行。** 默认私有可见和显式的共享动作把问题插件限制在一个人的视野里，但共享是一次真实的信任转移，值得第二个人看一眼。安装确认页展示的是它出现在哪、会读什么，而不是代码——专家不读代码。

**每一个数据提供者都是通往 RCI 系统的一条新读取路径。** 参数模式、缓存和脱敏限定了暴露面，但为某一块面板加的提供者，之后对所有插件都可用。

**提取错了，专家很难发现。** 漏掉一个条件、抬高一档置信度，都会以专家本人立场的身份进入系统。回执是唯一能暴露这件事的机制，而且要等系统已经照着做了之后。

**运行时加载插件，放弃了构建期对界面内容的掌握。** 清单与 `dataNeeds` 校验是它的替代；关掉这两项检查的部署两样都没有。

**创造模式可能产出杂物而非杠杆。** 跳过规格阶段，做出来的插件没人打开第二次。值得追踪的是留存，不是生成插件的总数。

**整条链依赖专家持续作答。** 限流保护他们的注意力，回执让作答显得值得；没有回执，这个通道会衰退成一个没人看的收件箱，而系统还在不停地问。
