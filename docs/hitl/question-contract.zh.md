# 提问契约

[English](question-contract.md) | 中文

系统怎么向专家提一个问题，问题怎么落进收件箱。这一节定义**提问器**（系统侧，每个 RCI 系统自己写）和**摄取**之间的契约。

本文描述的是正在生产运行的那个实例，它是新部署的基准。文中作为示例给出的数字和名字——限流值、分节标题——是那个实例的选择，出现处已标注；围绕它们的契约本身不是可选项。

提问质量决定整条链的质量。一个只写了"卡住了，求指点"的问题，专家要花十轮对话才问清现场；一个带完整现场的问题，专家第一条回复就能给方向。所以提问器的主要工作不是"问"，是**把现场整理成外部专家读得懂的材料**。

## 谁来提问

两类来源，共用一套格式与限流：

| 来源 | 触发 | 典型实现 |
|---|---|---|
| **工作 Agent 自述** | Agent 自己判断卡住了 | 它往约定路径写一份提问文件，例如 `work/<任务>/docs/EXPERT_QUESTION.json`；提问器收走后把文件改名为 `EXPERT_QUESTION.asked.<时间戳>.json`，Agent 看到就知道已被收集，不会重复问 |
| **巡检判定** | 外部规则发现停滞、反复失败、分数长期不动 | 巡检把任务挂上"攻坚榜"，提问器把新挂上的条目变成问题，`source.role` 标记为巡检 |

让 Agent 自己提问比纯规则判定有价值得多：它知道自己试过什么、卡在哪一层。但它也更容易滥发，所以提问器必须限流。

**提问器以定时任务运行**（例如随巡检每 30 分钟一次），而不是常驻进程。它的每一步都必须幂等：崩溃重跑不产生重复问题。

## 问题的字段

提问器往 `outbox.jsonl` 追加一行 JSON：

```json
{"type": "question",
 "id": "<stable unique id>",
 "title": "one line stating what is being asked (<=500 chars, the inbox title)",
 "detail": "optional elaboration",
 "options": ["optional quick answers", "at most six"],
 "context": "## sectioned background material\n...",
 "source": {"system": "mysys", "op": "task-name", "round": 151, "role": "patrol-board"}}
```

| 字段 | 必填 | 约束与用途 |
|---|---|---|
| `id` | 是（强烈建议） | 幂等键。重复摄取同一个 id 不会产生第二个问题，所以 outbox 被重写、偏移量丢失、提问器重跑都安全。推荐 `<任务>-<内容指纹>`，这样同一任务的不同问题不会互相覆盖 |
| `title` | 是 | 空标题的行直接丢弃。专家在收件箱里只看得到它，要能独立成立 |
| `detail` | 否 | 问题卡上标题下的一段 |
| `options` | 否 | 快捷回答，点一下作为一条消息发出。只在答案确实是枚举时给（"换方向 / 继续加轮次 / 放弃"）；开放式问题给选项会把专家往窄处引 |
| `context` | 否，但这是重点 | 背景材料，见下一节 |
| `source` | 是 | 问题的归属。它同时是 sink 的路由键（`when` 按 `question.source.*` 过滤）和注入时的目标定位。至少要有 `system`，以及能定位到具体任务的字段 |

`source` 的字段由系统自己定义，但一旦定下来就是契约：sink 路由、回执匹配、插件按来源渲染问题卡，都依赖它。

## 背景材料的分节

`context` 是一段 Markdown，用 `##` 二级标题分节。渲染侧把每个 `##` 拆成一张可折叠卡片，并按标题前缀给出一行导读。

一个成熟实例的分节顺序（CANNBench 舰队）：

| 分节 | 内容 | 为什么需要 |
|---|---|---|
| `## 背景` | 平台、评分口径、结论词表 | 外部专家不知道这套系统的词汇。后面所有数字都建立在这节上 |
| `## 原题：<名字>` | 要解决的问题本身、输入输出 | 先建立问题形状 |
| `## 当前设计` | 现在怎么实现的、卡在哪 | 一句话结论优先，不要逐行源码 |
| `## 当前实现结构` | 文件清单、关键常量、阶段划分 | 回答"数据流怎么走、怎么并行"的那一节 |
| `## 中间产物地图` | 每类中间结果在工作区的什么位置 | 专家想深挖时按图索骥，或直接让常驻 Agent 读给他 |
| `## 最近评测` | 每轮的通过数/总数、分数 | 看趋势，不是看单点 |
| `## 性能画像` | 最近一次性能评测的概览与最慢用例 | 定位哪些输入拖后腿 |
| `## 已尝试方向` | 每个方向 + 人话解释 + 结局 | **最重要的一节**：它防止专家重复推荐已证伪的路线 |
| `## 想请您指点` | 真正要问的问题 | 收束。前面都是材料，这节是请求 |

分节标题是约定，不是自由文本：渲染侧按前缀匹配导读文案。新增分节要同时在渲染侧登记它的导读，否则落到兜底文案。

写这些分节时的硬性要求：

- **术语要翻译。** `## 已尝试方向` 里每个方向名后面跟一句人话解释；结局词（"已证伪""云端实测有效""结果不正确"）在 `## 背景` 里给词表。专家是领域专家，不是这套系统的专家。
- **数字要带口径。** "84.1 分"本身没有信息；"本地 84.1 / 云端 73.8，本地分偏高的原因见背景节"才有。
- **长度要截断。** 每节设上限，超了截断并指向中间产物地图，让专家需要时让常驻 Agent 去读。背景材料是导读，不是转储。
- **要脱敏。** 提问器在写出之前过一遍脱敏：密钥、令牌、访问码、内部机制引用、与专家无关的内部资料路径，一律剔除。这一步在提问器里做，不能指望常驻 Agent 的提示词。脱敏规则要有单测。

## 限流与去重

提问器必须自己扛住三件事，状态存在它自己的状态文件里（例如 `hitl/bridge_state.json`）：

| 机制 | 建议值 | 理由 |
|---|---|---|
| **全局限流** | 所有来源合计每小时 ≤ 2 条新问题 | 专家的注意力是最稀缺的资源。收件箱一旦积压，整条链就失效了 |
| **同任务冷却** | 同一任务的下一个问题至少间隔 6 小时 | 一个任务同时只应有一个待解决的问题 |
| **内容去重** | 任务名 + 标题指纹 | 同一个卡点换个说法不算新问题 |

超过限额的提问不是丢弃，是**留在原地等下一轮**（Agent 写的提问文件不改名，巡检条目不标记已处理），这样它不会丢，只是延后。

## 落进收件箱

两条路，都可用，`id` 保证幂等：

**追加文件（推荐）。** 系统往 `outbox.jsonl` 追加一行。后端按配置的 `sources` 轮询（约 3 秒一次），记录每个文件的读取偏移量到 `data_dir/sources.json`。

文件路径这条路的好处是：**不依赖网站活着**。网站在升级、在重启、在崩溃，系统照样提问，等网站回来再摄取。这对一个要跑几周的 RCI 系统是决定性的。

轮询的实现细节，每一条都来自真实故障：

- 只处理到最后一个换行符为止，剩下的半行等它的换行符。否则会读到写了一半的 JSON。
- 文件大小小于已记录的偏移量，说明被重写了，偏移归零重读；`id` 幂等兜底。
- 单行解析失败就跳过这一行，不中断整个文件。
- 写入侧要 `flush` + `fsync`，否则崩溃时丢的是已经"交付"的问题。

**HTTP 提问。** 带服务令牌 `POST <base>/api/questions`，载荷同上。适合能直接访问网站的系统，省掉轮询延迟。

摄取时后端做三件事：建一个对话（标题取问题标题前 40 字）、写 `question.create`、在对话里放一条空的助手消息承载这个问题卡。然后触发通知。

## 通知

每个新问题给专家发一封邮件：标题、detail、谁问的、一个直接跳到该问题对话的按钮。SMTP 账号与收件人从环境变量读，站点公开地址从配置读。

通知结果落 `notify` 事件（发没发出去、失败原因），不要只写日志——"专家说没收到邮件"是会发生的，要能查。

邮件只对问题发，不对主动注入发。

## 回执

系统注入专家的观点之后，应该告诉专家它拿这条观点做了什么。回执也走 outbox：

```json
{"type": "receipt", "question_id": "<the question id>", "status": "injected",
 "detail": "injected at ...; six parallel verification lanes opened; best so far ...; conclusion: ..."}
```

或 `POST <base>/api/questions/<id>/receipt`（服务令牌）。

回执追加到该问题的 `insight.receipts`，专家在原对话里看得到。相同 `status` + `detail` 的回执视为重复，不重复追加。

**回执是闭环里最容易被省掉、也最不该省的一环。** 没有回执，专家只是在往一个黑洞里写建议；有回执（"你的方向已经注入，跑了 2000 轮，云端 75.9，还没超过基线，欢迎调整"），专家才会继续投入。建议至少两档：注入时的"已接收/已注入"，以及之后周期性的"进展更新"与收敛时的"效果回报"。
